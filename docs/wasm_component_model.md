# WebAssembly components

The implementation targets a checked subset of the Component Model.
`ComponentVersion` identifies the 0.2 MVP base and
`ComponentSpecRevision` pins the binary and ABI rules. The decoder accepts
the component header `00 61 73 6d 0d 00 01 00`. Full conformance is in progress.
[Implementation](../src/cps/wasm/component.nim) ·
[Pinned binary format](https://github.com/WebAssembly/component-model/blob/585526aa1f2c7f76f07557d16e265dede38b3acb/design/mvp/Binary.md) ·
[Pinned Canonical ABI](https://github.com/WebAssembly/component-model/blob/585526aa1f2c7f76f07557d16e265dede38b3acb/design/mvp/CanonicalABI.md).

## Supported profiles

| Area | Validation surface |
| --- | --- |
| Core linking | Multiple core modules within one component link functions, memories, tables, globals, and exception tags by identity in the full interpreter store. The linker validates the graph before invoking guest starts. |
| Canonical ABI values | The selected tests cover scalars, strings and lists, aggregate layouts, lift/lower alignment and bounds, maps, fixed-length lists, and context storage. |
| Resources | The suite covers nominal resource identity, owned and borrowed handles, and handoff between instances. |
| Typed core functions | Function-only recursive type groups and checked subtype matching. Core GC aggregate types remain outside the profile. |
| Async | Feature-gated callbacks, waitable sets and subtasks, stackful paths, futures and streams, host-owned endpoints, cooperative guest threads, and error contexts. These features have distinct test and target profiles. |

The source checks feature dependencies. Stackful support requires
`wasmComponentAsyncCallbacks`. Guest threads require stackful support.
`wasmComponentThreadSpawn` also requires `wasmFunctionReferences`. Pagers
and the stackful component executor have separate supported profiles.
Use the build profiles generated by the test runner for target checks.

## Check conformance and target coverage

Use `wasm-tools 1.263.0` for the checked fixtures. The upstream test runner
takes a checkout at the pinned revision:

```sh
mkdir -p build/wasm-component
git clone https://github.com/WebAssembly/component-model.git build/wasm-component/spec
git -C build/wasm-component/spec checkout --detach \
  585526aa1f2c7f76f07557d16e265dede38b3acb
python3 tools/run_wasm_component_spec.py build/wasm-component/spec
```

The runner converts selected upstream WAST to binaries and assertions and
runs them through Nim. It reports the covered assertions and skipped cases.
Add a focused QEMU option to exercise native target builds:

```sh
python3 tools/run_wasm_component_spec.py build/wasm-component/spec \
  --qemu-core-function-types --qemu-map --qemu-fixed-list
python3 tools/run_wasm_component_spec.py build/wasm-component/spec \
  --qemu-callbacks --stackful
```

The async target paths differ by core. For example, the callback profile
covers all three CPUs while its guest-subtask and cancellation cases run
on M0/D0. LP has a separate extended-RAM subtask diagnostic. Record which
firmware memory profile and feature flags your result used.

The [upstream runner](../tools/run_wasm_component_spec.py) lists the
feature-specific switches. The [local fixture runner](../tools/run_wasm_component.py)
checks repository fixtures. See [Core WebAssembly](wasm_full_baseline.md)
for the common interpreter and toolchain.

The [component reference snapshot](https://github.com/gabearro/bl808-hal-nim/blob/eb932dddbb56ac5131b3d398e5463f18008fc639/docs/wasm_component_model.md)
records the previous detailed coverage, fixture tables, and per-core measurements.
