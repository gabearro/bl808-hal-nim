# Hardware validation

[hw_validate.py](../tools/hw_validate.py) builds examples from the
[hardware test manifest](../tools/hardware_validation.json), runs them on a
BL808, and checks the configured console markers. The harness holds a hardware
lock during live runs. Keep one harness work directory for operations sharing a
board and its serial adapter.

## Start with discovery

```sh
make venv
.venv/bin/python tools/hw_validate.py --list
```

Set `UART_PORT` to the detected runtime UART. For example, on Linux:

```sh
UART_PORT=/dev/ttyUSB0
.venv/bin/python tools/hw_validate.py --preflight --uart "$UART_PORT"
.venv/bin/python tools/hw_validate.py --test m0_hello_nim_test --build-only
```

Use a 3.3 V serial adapter with RX on Ox64 GPIO14, TX on GPIO15, and a shared
ground. The default baud is 230400. Pass `--flash-port` as well as `--uart`
when flashing and runtime use separate adapters. Rediscover the device names
after disconnecting the hub or adapter.

JTAG defaults to M0 with `pine64jtag.cfg` and `tgt_e907_v2.cfg`. The usual Ox64
TMS, TDO, TCK, and TDI pins are 6, 7, 12, and 13. The harness prefers
`../openocd-had/src/openocd` when present and otherwise uses `openocd` on
`PATH`. Use `--ftdi-reset-sudo` where USB adapter reset needs privileges.
See [bench-specific reset notes](../AGENTS.md#reset-and-ftdi-behavior) for this
workspace's wiring.

## Pick a transport

| Mode | Operation |
| --- | --- |
| Default UART | Enters the BL808 ROM loader and uses [upload.sh](../tools/upload.sh) and the vendor tool to write flash. |
| `--rom-flash` | Uses the BL808 serial ROM loader to start a RAM flash anchor, then writes, reads back, and reboots over UART. Requires manual BOOT and power control. |
| `--jtag-load` | Loads a RAM-linked test and starts it through JTAG. Choose this for temporary smoke tests. |
| `--jtag-flash` | Writes persistent flash using an M0 JTAG flash stub. |
| `--uart-anchor-flash` | Usually starts a temporary M0 anchor through JTAG, then streams verified flash writes over UART. Add `--uart-anchor-existing` when a compatible anchor is already running. |

`--build-only` compiles without accessing hardware. `--dry-run` shows the
planned build, transport, and reset. Use one flash or load mode per invocation.

### Temporary JTAG smoke test

```sh
.venv/bin/python tools/hw_validate.py --test m0_hello_nim_test \
  --jtag-load --uart "$UART_PORT"
```

For the smoke tier use `make hw-smoke-jtag UART_PORT="$UART_PORT"`.
`make hw-allcore-jtag UART_PORT="$UART_PORT"` runs the all-core RAM test.
RAM loading can replace the programs running on the touched cores until reset.

### Persistent UART-anchor flash

On a bench with M0 JTAG and UART, dry-run this command first, then run it
without `--dry-run` to flash:

```sh
.venv/bin/python tools/hw_validate.py --test m0_hello_nim_test \
  --uart-anchor-flash --uart-anchor-reset-after-flash --no-jtag-reset \
  --uart "$UART_PORT" --dry-run
```

`--no-jtag-reset` lets the harness halt and load the anchor without issuing
OpenOCD `reset halt`. The anchor verifies the writes and requests a software
power-on reset that includes M0. The equivalent procedure covers FreeNetRadio
once its build inputs are set. See [FreeNetRadio](freenetradio.md).

Use these when a persistent UART anchor is already active:

```sh
.venv/bin/python tools/hw_validate.py --uart-anchor-probe \
  --uart-anchor-existing --no-jtag --uart "$UART_PORT"
.venv/bin/python tools/hw_validate.py --test m0_hello_nim_test \
  --uart-anchor-flash --uart-anchor-existing --no-jtag \
  --uart-anchor-reset-after-flash --uart "$UART_PORT"
```

The second command replaces the anchor in flash. Future writes need a
JTAG-loaded anchor, the ROM route, or another persistent anchor. For a reboot
without flash writes, use `--uart-anchor-reboot` with the matching anchor
options. An existing-anchor probe leaves the running firmware in place.
A probe without `--uart-anchor-existing` loads the anchor into M0 RAM.

### Flash using the ROM and UART

```sh
.venv/bin/python tools/hw_validate.py --test m0_hello_nim_test \
  --rom-flash --uart "$UART_PORT"
```

When prompted, remove board power, hold BOOT while restoring power, release
BOOT, and continue at the terminal. The harness writes and verifies boot2,
the partition tables, and the selected firmware as required by the image.
Set `BL808_BOOT2` to a known-good headered BL808 boot2 image if the harness
cannot find its SDK copy. Set `BL808_FW_BOOTINFO` to a verified template if
the firmware wrapper needs an override.

For a prebuilt wrapper, check its board, flash start, and exclusive erase end
before calling `--uart-anchor-flash-image`. The recovery manifest generated by
`--uart-anchor-build-only` includes the addresses and checksums for the
persistent-anchor bundle. Use that manifest for recovery-image installs.

## Read a result

Under the default `build/hw-validation` work directory, start with
`logs/<test>.primary.uart.log`, then the per-test OpenOCD log, reset log, and
anchor banner log when present. Binaries and ELFs are grouped under
`bin/<test>/`. Set `--work-dir` for a separate record of a comparative run.

For a focused snapshot, pass an aligned address and word count as
`--jtag-read ADDRESS:WORDS`. Use the ELF of the installed build to resolve
addresses. The harness can also capture test-specific registers and
memory on failure. Stop before
restarting a board if its live state is the evidence you need.

| Symptom | Check |
| --- | --- |
| No UART banner | Check port, baud, and wiring. Confirm a real reset or anchor reboot occurred. |
| JTAG `IDCODE=0` or attach failure | Check the mux, pins, permissions, and FTDI adapter. Rediscover ports after adapter recovery. |
| Anchor banner with no acknowledgment | Verify that the selected anchor is running and that the acknowledgment mode matches the transport. |
| ROM entry fails | Repeat the BOOT and power sequence. Use [bl808_isp.py](../tools/bl808_isp.py) `probe` against the flash UART to check loader entry. |
| Firmware loops before the first log | Snapshot PC, SP, MEPC, MCAUSE, and MTVAL. Resolve addresses in the matching ELF, then bisect the boot stages with debugger breakpoints. |

An FTDI USB reset resets the adapter. On an Ox64 J6 header the target reset
line is unwired, so a reported nSRST pulse alone does not establish a board
reset. Use the anchor reboot or a verified physical reset for that purpose.
See the [bench recovery notes](../AGENTS.md#host-recovery-when-uart-anchor-and-jtag-are-silent).

For macOS BLE host-action tests, check CoreBluetooth authorization first:

```sh
.venv/bin/python tools/run_macos_ble_helper.py permission --debug
```

Use [Profiling](profiling.md) for sampling a running target. The resident
application console and USB flash-anchor path have their own
[guide](usb_uart_anchor.md).
